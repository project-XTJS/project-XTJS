### 1. P1：切换项目加载失败后，显示上一项目的审查结果

位置：[ReviewPage.jsx:4665](/root/project_XTJS/XTJS-frontend/src/pages/ReviewPage.jsx:4665)、[ReviewPage.jsx:4769](/root/project_XTJS/XTJS-frontend/src/pages/ReviewPage.jsx:4769)。

`handleProjectChange` 更新当前项目并清理部分界面状态，但没有清理 `results` 和 `allAlerts`；`loadData` 的失败分支同样没有清理这两个值。

浏览器复现：成功打开 A，再切换 B，让 B 的结果接口返回 503。页面提示加载失败，但 B 的项目标题下仍能进入“项目 A 专属签章问题”，且“导出报告”按钮仍可用。已证明结果串显示和导出入口未禁用；本次没有向真实项目保存、导出报告或断言真实项目已被污染。

最小修复：切项目时清空结果及相关引用；失败时保持明确失败状态；编辑、预览和导出必须校验当前加载结果所属项目与选择项目一致。补充 A 成功→B 失败的浏览器用例。

证据：[浏览器复现结果](/data/llm_cpu_gpu_poc/experiments/full_code_audit_20260914/frontend-reproduction.json)、[模拟页面截图](/data/llm_cpu_gpu_poc/experiments/full_code_audit_20260914/stale-review-demo.png)。

### 2. P1：人工复核保存失败，旧内容却已经被覆盖

位置：[document_blob_store.py:92](/root/project_XTJS/project-XTJS/app/service/document_blob_store.py:92)、[postgresql_service.py:1172](/root/project_XTJS/project-XTJS/app/service/postgresql_service.py:1172)、[postgresql_service.py:1244](/root/project_XTJS/project-XTJS/app/service/postgresql_service.py:1244)。

人工复核副本使用文件名加文档 ID 的固定对象键，先覆盖对象，再更新数据库。数据库事务无法撤销已经完成的对象存储写入。

隔离复现：先保存 OLD_MANUAL，再注入数据库约束错误，尝试保存 NEW_MANUAL。数据库操作失败，原对象键不变，但重新读取已经变成 NEW_MANUAL。因此“接口保存失败”不等于“原内容保留”。

最小修复：复核副本也使用每次写入的新版本对象键，数据库提交成功后再切换引用；提交失败保留原对象。此前的不可变版本键保护主要覆盖项目结果，不能据此认为所有对象写入均已受保护。原始 OCR、独立招标审查结果也存在固定键写法，后续应按各自更新路径补充同类故障测试，不能只改一个调用点。

### 3. P1：更换文件地址后，仍使用旧 OCR、旧哈希和旧结果

位置：[postgresql_service.py:1318](/root/project_XTJS/project-XTJS/app/service/postgresql_service.py:1318)、[postgresql.py:5687](/root/project_XTJS/project-XTJS/app/router/postgresql.py:5687)。

文档更新接口允许修改 `file_url`，只更新名称、URL 和时间，没有重置 `extracted`、OCR 对象引用、源文件哈希及相关项目结果。路由清除 Redis/预览缓存，不能清除数据库里的旧识别状态。

隔离复现：将已识别文档换成新 URL，仍然 `extracted=true`，内容为 OLD_OCR，哈希为旧值，项目审查结果也保持旧值。正常断点续跑按已提取状态跳过，无法自动纠正。

最小修复：单纯重命名继续允许；实际更换原文件应创建新文档并重新关联，或原子地失效该文档的派生内容及相关结果。重新分析前明确提示结果已过期。保留旧版本，避免直接不可逆清空。

### 4. P1：对象删除 API 可删除仍被数据库引用的文件

位置：[file.py:53](/root/project_XTJS/project-XTJS/app/router/file.py:53)。

`DELETE /api/files/objects/{object_name}` 直接调用对象删除，无文档/结果引用检查，无逻辑删除协调。路由有登录保护，但这不能保障引用完整性。

隔离复现：用真实路由删除内存存储中仍被文档引用的 OCR 对象，返回 `deleted`；之后读取该文档抛出 `BlobReadError`。如果作用于真实对象，会留下“数据库记录存在，文件不存在”的问题。

最小修复：禁止通过通用入口删除仍被引用的对象；实际文件回收走应用逻辑删除后的专用流程。本平台文档明确普通登录用户共享项目功能，因此本项不是把共享项目权限本身判为 bug，而是物理删除绕过引用维护。

### 5. P2：删除标书关联后，上传完整状态和已存结果未同步

位置：[postgresql_service.py:2262](/root/project_XTJS/project-XTJS/app/service/postgresql_service.py:2262)、[upload_manifest.py:20](/root/project_XTJS/project-XTJS/app/service/upload_manifest.py:20)。

上传完整状态读取已保存的 manifest 标志。创建关联时会对账，但删除关联只执行 DELETE，不更新 manifest，也不让旧审查结果失效。关联修改和文档软删除路径存在相同的状态维护缺口，需要一并核对。

隔离复现：完整两组标书删除一组关联后，实际剩一组；刷新仍为 `upload_complete=true`、`parsing_status=3`；保存结果还包含两个投标人。

最小修复：所有关联增删改都统一维护预期材料清单、当前关联和结果版本。若删除是用户有意移除单位，应同步修改预期清单；若仅移除了必要关联，应明确标记不完整。两种情况都应让受影响旧结果过期，不能只清缓存。

### 6. P2：同一缺失文件并发补传，会增加重复投标关联

位置：[postgresql_batch.py:1725](/root/project_XTJS/project-XTJS/app/router/postgresql_batch.py:1725)、[postgresql_batch.py:851](/root/project_XTJS/project-XTJS/app/router/postgresql_batch.py:851)、[postgresql_service.py:330](/root/project_XTJS/project-XTJS/app/service/postgresql_service.py:330)。

补传先检查上传状态，再执行上传和写回。两个请求都能在状态更新前通过检查。后一个请求可以覆盖同一 slot 的 document_id，并为新文档再创建一组关联。单次 SQL 更新有锁，但没有覆盖整个补传操作的幂等保障。

隔离复现：两客户端同时补同一技术标，控制第二个上传较晚完成。预期两组，最终出现三组关联，仍显示 `upload_complete=true`。测试没有写真实 OSS。

最小修复：对项目与文件 slot 建立原子的领取状态和请求幂等标识，完成时校验版本；关联以逻辑投标组唯一，禁止同一组因重试增生。仅禁用前端按钮不足以覆盖两个客户端和网络重试。

### 7. P2：结果接口仍会阻塞同一进程的其他请求

位置：[postgresql.py:4437](/root/project_XTJS/project-XTJS/app/router/postgresql.py:4437)。

`async` 结果路由在缓存未命中或强制刷新时直接执行同步数据库及对象存储读取。已修复的项目列表、详情及 OCR 状态接口并不覆盖此处。

隔离复现：模拟结果读取耗时 300 ms，在同一事件循环安排 20 ms 探针，探针约 321 ms 后才执行。证明存储变慢时会阻塞同一 worker 的其他协程；不是实际 OSS 故障注入，也不能据此量化生产所有请求的延迟。

最小修复：将完整同步读取和组装路径移入线程池，同时保留存储超时及并发上限。人工复核、单项结果等同步调用也需检查。静态扫描中的调用数量不能直接当作 bug 数量，部分调用位于同步闭包中。

### 9. P2 / P3：合并标书双角色上传后，技术查重范围及重复计算不够准确

位置：[duplicate_check/service.py:239](/root/project_XTJS/project-XTJS/app/service/analysis/duplicate_check/service.py:239)、[document_ingest_service.py:44](/root/project_XTJS/project-XTJS/app/service/document_ingest_service.py:44)、[bid_document_review.py:1531](/root/project_XTJS/project-XTJS/app/service/analysis/bid_document_review.py:1531)。

### 11. P2：修改或重置密码不会使已经签发的令牌失效

位置：[user_service.py:198](/root/project_XTJS/project-XTJS/app/service/user_service.py:198)、[auth_dependencies.py:25](/root/project_XTJS/project-XTJS/app/router/auth_dependencies.py:25)。

认证验证签名、过期和用户启用状态，不比较口令版本。密码重置只更新密码哈希等字段。

隔离用户表复现：重置密码成功后，原令牌仍可通过认证；停用账号则立即返回 401。运行配置的令牌有效期为 120 分钟，旧令牌可继续使用到其原到期时间。测试使用临时签名密钥，没有生成可用于真实平台的审计令牌。

最小修复：增加专门的口令/会话版本或口令变更时间，签发及认证时校验，改密码时递增。不要直接用普通 `update_time`，因为登录或修改显示名也会改它。

## 建议修复顺序与验收标准

1. 先修 1—4：串项目结果、失败保存覆盖、更换文件后旧结果、物理删除绕过引用。这些直接关系到“内容是否属于当前文件/项目”和“失败后旧数据是否仍可靠”。
2. 再修 5—7：增删改关联的完整性、补传幂等和事件循环阻塞。继续允许人工补传和人工继续，不必先做复杂自动恢复。
3. 再处理 8—11：主体识别、合并文件范围、文档枚举及令牌失效。名称修复保留 OCR 原文，算法改动必须对多项目回放，控制误判变化。
4. 同步补充 12 的测试入口及回归用例。

对应验收：B 加载失败时不显示 A 的任何结果；保存失败仍读到上个已提交版本；源文件变化后旧结果明确过期；引用对象不能被通用删除入口删除；增删改关联后数量/清单/结果版本一致；并发补传同一 slot 最多保留一份有效绑定；存储慢请求不阻塞同 worker 的轻量请求；密码变化使旧会话失效。
