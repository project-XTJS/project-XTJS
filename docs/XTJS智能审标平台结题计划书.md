## 1. 结题目标

本计划用于完成 XTJS 智能审标平台的成果确认、质量验收、版本冻结、数据与运维交接，并形成可追溯的结题档案。

结题不代表系统不再维护，而是确认当前阶段已经形成可独立运行的交付版本。后续新增规则、模型优化和业务调整，应转入运维或下一阶段迭代管理。

## 2. 当前实际情况

### 2.1 项目定位

XTJS 是一套面向招投标文件的智能辅助审查系统，当前已形成以下业务闭环：

```text
用户登录 → 项目及文件上传 → 分阶段 OCR → 多项智能审查
        → PDF 定位与人工复核 → Word/JSON 报告导出
```

系统由两个 GitHub 仓库组成：

| 子系统 | 技术实现 | 主要职责 |
| --- | --- | --- |
| 后端 `project-XTJS` | FastAPI、Python、PaddleOCR-VL、PyMuPDF | 文件处理、OCR、审查计算、数据接口、认证、报告生成 |
| 前端 `XTJS-frontend` | React 18、Vite、Nginx | 项目管理、分析执行、结果复核、文档预览、用户管理 |
| 推理服务 `xtjs-vllm` | vLLM、GPU | 为 PaddleOCR-VL 提供推理加速 |
| 数据库 | 阿里云 RDS PostgreSQL | 项目、文档关系、结果和用户数据 |
| 文件存储 | 阿里云 OSS | 原始 PDF、OCR JSON、复核数据、报告和预览缓存 |
| 缓存 | 阿里云 Redis/Tair | 项目、结果、OCR 状态和预览缓存 |

### 2.2 已实现业务能力

1. 项目创建、文件夹批量上传和手工成组上传。
2. 招标文件、商务标、技术标的分阶段 OCR 和中断续跑。
3. 上传前文件结构校验、同名项目阻止复用、PDF 作者属性冲突预警。
4. 独立招标文件审查及历史记录管理。
5. 商务标完整性、一致性、签字盖章日期、报价合理性和分项报价检查。
6. ★/△偏离项目审查。
7. 商务标查重、技术标查重和人员复用检查。
8. 问题对应 PDF 页码定位、高亮预览和原文件下载。
9. 人员名单、识别内容和偏离状态的人工复核与重新审查。
10. Word 项目审查报告和 JSON 结果导出。
11. Word 报告包含项目基本信息、投标人名单及源 PDF 文件属性。
12. JWT 登录、失败锁定、密码修改和管理员用户管理。

### 2.4 总体技术架构

项目采用前后端分离、应用与数据资源分层的架构。浏览器只访问 Nginx 前端入口，`/api` 请求由 Nginx 转发给 FastAPI；FastAPI 负责业务编排，并分别连接 PostgreSQL、OSS、Redis/Tair 和 vLLM。大文件不直接长期存入数据库，数据库主要保存结构化记录和对象引用。

```text
浏览器
  │
  ▼
Nginx + React 前端
  │ /api
  ▼
FastAPI 后端
  ├── RDS PostgreSQL：项目、文档关系、结果、用户
  ├── OSS：PDF、OCR JSON、复核内容、报告、预览缓存
  ├── Redis/Tair：查询与进度缓存
  └── vLLM + NVIDIA GPU：PaddleOCR-VL 推理
```

该架构的结题价值在于：业务页面、审查逻辑、推理资源和数据资源可以分别维护；数据库避免承载大量 PDF 和超大 JSON；推理接口不直接暴露公网；前端通过统一 API 使用所有能力。

### 2.5 前端技术栈与建设成果

| 项目 | 当前实现 |
| --- | --- |
| 核心框架 | React 18.2、React DOM 18.2 |
| 路由 | React Router 6，使用 HashRouter |
| 构建工具 | Vite 4 |

| 样式 | 项目自定义 CSS，无外部 UI 组件库依赖 |

前端围绕实际审标流程建设了五个页面：项目管理、招标文件审查、分析中心、结果审核和用户管理。主要成果包括：

1. 将长耗时 OCR 拆为招标、商务和技术三个阶段，并展示文件级、页级进度。
2. 将审查能力按业务条件门控，商务标未完成时不能误执行技术阶段分析。
3. 提供项目下拉选择、结果类型筛选、文件筛选和审查项筛选，支持大量结果逐项审核。
4. 将问题卡片与 PDF 页码、证据文字和高亮框关联，减少人工翻页时间。
5. 支持人员名单编辑、商务识别值修正、偏离状态修正和重新分析。
6. 导出前将人工“忽略/保留”状态转换为报告中的通过/不通过状态。
7. 使用 Nginx 托管静态资源并反向代理后端，配置大文件上传和较长 OCR 请求超时。

前端未引入 Redux 或大型组件库，部署产物较简单；但 `ReviewPage` 承载功能较多，后续维护应继续拆分为结果筛选、PDF 预览、人员确认、人工复核和导出等独立模块。

### 2.6 后端技术栈与建设成果

| 项目 | 当前实现 |
| --- | --- |
| 语言与运行时 | Python 3.10—3.12，生产镜像使用 Python 3.12 |
| Web 框架 | FastAPI 0.104.1 |
| Web 服务器 | Uvicorn 0.24 |
| 配置管理 | Pydantic Settings、dotenv、环境变量 |
| 数据校验 | Pydantic Schema |
| 文档上传 | `python-multipart`，流式接收 PDF |
| 数据库访问 | psycopg2 连接池和原生 SQL |
| 辅助任务依赖 | Celery 5.6 已保留在依赖中 |

后端采用路由、Schema、服务、分析模块和基础设施适配器分层。FastAPI 的依赖注入用于统一取得数据库、缓存、对象存储、OCR 和分析服务。所有业务接口统一进行认证，并以统一响应结构返回请求编号、状态和数据，便于前端处理和日志追踪。

从结题成果看，后端已经完成从早期集中式代码向模块化服务的演进：合规审查、偏离、查重、分项报价、报价合理性、人工复核和 OCR 均已有独立目录或服务，复杂规则不再全部堆积在单一路由中。

需要说明的是，当前生产 Compose 没有单独部署 Celery Worker。Celery 属于保留依赖，不应在结题材料中描述为当前生产必需服务；现网需要启动的是应用、vLLM 和前端三个容器。

### 2.7 API、状态机与业务编排

后端现有约 79 个 HTTP 路由，覆盖认证、项目、文档、关系、OCR、分析、人工复核、预览、报告和独立招标审查。API 层的重要建设成果包括：

- 项目、文档和项目文档关系使用稳定标识符关联。
- OCR 使用 `parsing_status` 表示已上传、招标完成、商务完成和技术完成四个阶段。
- 中断恢复接口只规划未完成文档，避免已完成 OCR 被重复执行。
- 分析中心按阶段组合服务，结果经统一 Normalizer 转换为前端可消费结构。
- 人工识别输入、人员草稿和工作流剔除范围可以持久化，不依赖浏览器临时状态。
- 项目文件夹上传发现同名项目时返回冲突，不自动复用旧项目，从机制上降低跨项目串文件风险。

该状态机是系统可操作性的核心：它既控制按钮是否可用，也决定哪些文档能够进入对应分析。结题验收应重点验证异常中断、刷新页面和重启容器后状态仍然连续。

### 2.8 数据库技术栈与数据模型

系统数据库采用 PostgreSQL，生产部署使用阿里云 RDS。后端以 psycopg2 原生 SQL 和连接池访问，没有把 ORM 作为核心数据访问方式。数据库结构通过 Flyway SQL 文件版本化，目前仓库包含 14 个迁移文件。

核心数据模型如下：

| 表 | 作用 |
| --- | --- |
| `xtjs_projects` | 项目名称、解析状态、报告地址、时间和删除状态 |
| `xtjs_documents` | 文档类型、文件信息、OCR/复核对象引用和解析状态 |
| `xtjs_project_documents` | 项目与招标、商务、技术文档的绑定关系 |
| `xtjs_result` | 项目分析结果、前端展示结果、人工复核输入及对象引用 |
| `xtjs_users` | 用户、密码摘要、权限、启停和登录锁定信息 |
| `xtjs_tender_reviews` | 独立招标文件审查历史和结果 |

数据模型经历了规范化调整：项目与文档通过关系表关联，结果使用 JSONB 保持分析结构的扩展能力，大体积内容逐步外置到 OSS。该方案适合规则持续变化的智能审查系统，但结题后仍应维护字段字典和数据保留策略，避免 JSON 结构长期缺少版本约束。

### 2.9 对象存储与冷热数据分层

系统通过 MinIO Python SDK 访问兼容 S3/MinIO 接口的阿里云 OSS。当前对象存储承担：

- 招标文件、商务标和技术标原始 PDF；
- OCR 结构化内容；
- 人工复核后的文档工作副本；
- 项目分析大结果；
- Word 报告；
- PDF 页面预览缓存。

原文件按“项目/文件角色/投标人/文件名”分层组织，数据库保存对象键或文件 URL。大 JSON 采用压缩对象存储，避免数据库行持续膨胀；访问报告和原文件时使用受控的临时链接。

该设计已经解决早期大 JSON 与原文件直接占用数据库的问题，也是项目数据可扩展的关键成果。结题必须补齐 OSS 生命周期、误删除防护、RAM 最小权限和恢复验证，尤其不能只验证“能读”，还要验证生产所需的上传、更新和报告写入。

### 2.10 Redis/Tair 缓存与长任务支撑

生产环境使用阿里云 Redis/Tair，后端 `redis` 客户端用于缓存项目列表、项目详情、分析结果、OCR 状态和预览元数据。Compose 中通过环境变量配置缓存地址、键前缀和不同数据的 TTL。

缓存的主要价值是降低项目轮询和 PDF 预览对 RDS、OSS 的重复访问，尤其适合 OCR 期间前端每隔数秒读取进度的场景。后端健康接口会报告缓存连接状态，当前为 healthy。

Redis 中的数据不是唯一业务副本。项目、文档和结果的持久化仍以 RDS 和 OSS 为准，因此结题恢复演练应同时验证“Redis 清空后系统仍能从持久层恢复正常查询”。

### 2.11 OCR、版面分析与图像处理

| 技术 | 用途 |
| --- | --- |
| PaddleOCR 3.4 文档解析能力 | PDF 页面文字、版面和结构化内容识别 |
| PaddleOCR-VL 1.5 模型 | 复杂扫描件、多模态文档理解 |
| OpenCV 4.10 | 图像预处理与视觉辅助处理 |
| Pillow、NumPy | 页面图像和数组处理 |
| PaddleNLP、Torch、Transformers | 模型和文本分析运行基础 |

OCR 结果不仅保存纯文本，还尽量保留 `layout_sections`、`logical_tables`、页码和边界框。这些结构是完整性、评分表、分项报价、印章签名、人员抽取和前端高亮的共同基础。

系统已经实现 GPU 优先、CPU 回退、页面进度、单卡并发控制和 OCR 结果缓存。当前默认每个设备只允许一个文档级在途任务，以控制显存占用和跨文档争抢。结题验收应覆盖文本型 PDF、普通扫描件、旋转页、低清页和复杂表格，不应只使用排版规范的样本。

### 2.12 vLLM 与 GPU 推理加速

生产环境单独运行 `xtjs-vllm:v0.22.1`，加载 `PaddleOCR-VL-1.5-0.9B` 模型，并通过 Docker 内网的 OpenAI 兼容接口为后端提供推理能力。vLLM 端口不映射到公网，后端通过服务名访问。

当前硬件为 NVIDIA L20。vLLM 配置限制 GPU 显存利用率，并设置最大上下文和批处理 Token，以兼顾 OCR 吞吐与其它 GPU 任务。模型文件挂载自 OCR 运行卷，避免每次重建应用镜像都重复打包权重。

该拆分使 Web 应用重启不必重新加载大模型，也便于单独检查模型健康。系统同时保留 `native` 推理后端作为回退路径。结题交付应记录实际使用的模型目录、模型版本、vLLM 启动参数、CUDA 兼容关系和回退验证结果。

### 2.13 智能审查算法与规则体系

系统并非只调用单一大模型，而是组合了结构化解析、规则匹配、词法相似度、语义向量、算术校验和人工确认。

| 能力 | 主要技术方法 | 当前输出 |
| --- | --- | --- |
| 独立招标审查 | 金额/比例解析、复选框状态、评分区间和合计规则 | 预算、限价、保证金、付款、评分等通过/异常/待复核项 |
| 完整性检查 | 招标目录与附件模板并集、同义词、标题归一和词法匹配 | 必备材料是否存在及证据页 |
| 一致性检查 | 模板正文、结构化字段、标题兼容和 BGE 语义匹配 | 模板与响应内容的一致/缺失/待复核结论 |
| 签字盖章日期 | 签名、印章、日期锚点和截止时间规则 | 缺签字、缺盖章、日期异常及定位 |
| 报价合理性 | 中文金额、数字金额、最高限价、下浮率规则 | 大小写一致性、限价和比例异常 |
| 分项报价 | OCR 表格重建、数值归一、行列及总价算术校验 | 分项与总价不一致问题 |
| 偏离审查 | ★/△条款提取、关键词、SequenceMatcher 和语义判定 | 强制项、加分项的响应、缺失和偏离状态 |
| 商务/技术查重 | 文本规范化、精确重复、相似度和聚类 | 跨文件重复片段、文件及页码范围 |
| 人员复用 | 人名与岗位抽取、黑名单过滤、跨文件聚合 | 人员草稿和确认后的疑似复用结果 |
| 作者属性预警 | PyMuPDF 读取 PDF author/creator 等元数据 | 不同投标文件的相同属性风险提示 |

规则与模型结合是当前项目的主要技术成果：明确可计算的金额、日期和合计采用规则；标题变体和正文含义采用词法或语义匹配；不确定内容进入待复核；人员和最终问题状态保留人工确认入口。

结题时不能只统计“发现了多少问题”，还应按样本标注计算典型审查项的命中、误报和漏报，并记录规则适用范围。PDF 元数据相同只能作为预警线索，不能直接作为围标或串标认定。

### 2.14 PDF 处理、证据定位和报告生成

系统使用 PyMuPDF 读取 PDF 页数、文本、元数据和页面图像，结合 OCR 边界框生成证据预览。前端能够跳转指定页、显示高亮、切换页面、缩放和下载原文件。

报告使用 `python-docx` 生成 Word 文档，包含：

- 项目名称、采购人、代理机构和查询日期；
- 投标人名单及联系人；
- 招标、商务和技术源文件属性；
- 审查总览、对应文件和明细；
- 人工保留、忽略后的颜色和结论状态。

源文件属性表采用独立横向页面和固定列宽，后续正文恢复纵向。标题、作者、主题、关键字、创建程序和制作工具取自 PDF 原始元数据，源文件未填写时显示 `-`，不会用 OCR 推测值冒充文件属性。

从结题角度，证据定位和可导出报告使系统结果具备人工复核与归档条件，是从“算法演示”转为“业务工具”的关键环节。

### 2.15 认证、权限与安全控制

| 安全项 | 当前实现 |
| --- | --- |
| 登录认证 | JWT Bearer Token，HS256 |
| 密码保存 | bcrypt 摘要，不保存明文密码 |
| 登录保护 | 失败次数累计和临时锁定 |
| 账号状态 | 启用、停用、逻辑删除 |
| 权限等级 | 普通、中级、高级、管理员四级 |
| 管理保护 | 非管理员不能进入用户管理；不能删除自己或最后一个管理员 |
| 对象访问 | 私有 OSS、实例 RAM 角色、临时访问链接 |
| 模型接口 | vLLM 仅在 Docker 内网开放 |

认证功能解决了早期业务接口公开访问的问题。当前所有业务接口均要求登录，管理员接口额外要求管理员等级。

现阶段权限体系仍以“是否管理员”为主要差异，普通、中级和高级尚未细分项目创建、删除、分析和导出权限。这一点已明确列入本期边界和后续建议，不能在结题材料中表述为四级业务授权已经全部落地。

### 2.16 Docker、云资源与部署运维

系统使用多阶段 Docker 构建：前端先在 Node 20 环境生成静态文件，再复制到 Nginx；后端精简镜像基于 Python 3.12 Slim，安装 Paddle GPU、Torch、OCR 和分析依赖。Compose 叠加基础、GPU、精简镜像和 vLLM 配置，以适配当前生产环境。

生产运行组件为：

| 容器 | 职责 | 重启策略 |
| --- | --- | --- |
| `xtjs-frontend` | Nginx 和前端静态资源 | `unless-stopped` |
| `project-xtjs` | FastAPI、OCR 编排和分析 | `always` |
| `xtjs-vllm` | GPU 推理服务 | `unless-stopped` |

RDS、OSS 和 Redis/Tair 使用云托管资源，宿主机不再运行对应数据库、MinIO 或 Redis 容器。该方式减少本机有状态服务维护，但增加了对 VPC、白名单、RAM 角色和云资源可用性的依赖。

当前日志采用结构化 JSON，支持日志级别、目录、大小和保留天数配置；应用提供健康接口，vLLM提供健康与模型列表接口。结题后建议把三个健康检查接入持续监控和告警，而不只依赖人工执行 `docker ps`。

### 2.17 测试、版本与工程化现状

后端仓库已有针对招标规则、附件标题、完整性、分项报价、OCR 恢复和项目文件夹检查的测试文件；前端配置 ESLint 和生产构建，但缺少单元测试及端到端测试框架。

Git 已形成前后端双仓库历史，数据库迁移脚本随代码版本化，Docker 配置和部署指南已经入库。这些内容构成可交接的工程基础。

当前工程化短板包括：

1. 尚无正式 Git Release/Tag 和与提交号绑定的镜像标签。
2. 后端同时存在 unittest 与 pytest 风格，执行入口未统一。
3. 实验测试引用了当前生产代码树中不存在的模块。
4. 前端没有自动化 E2E。
5. 镜像没有写入 Git SHA、构建日期和版本标签。
6. 一次性恢复脚本硬编码容器 ID，不适合作为长期运维基线。

这些不是对现有业务能力的否定，但会影响结题版本的可复现性和质量证据完整度，因此已纳入结题前必须工作。

### 2.18 技术建设成果总结

从技术演进看，本项目已经完成以下阶段性转变：

1. 从文件上传和简单文本处理，发展为具有版面、表格、页码和边界框的结构化 OCR 流程。
2. 从单一规则检查，发展为规则、词法、语义、算术和人工复核组合的多维审查体系。
3. 从同步长任务，发展为分阶段执行、进度显示和中断续跑。
4. 从数据集中保存，发展为 RDS 结构化记录、OSS 大对象、Redis 缓存的分层存储。
5. 从无认证页面，发展为 JWT、密码摘要、锁定和管理员保护的账号体系。
6. 从结果列表，发展为 PDF 证据定位、人工修订和 Word/JSON 归档闭环。
7. 从本地模型耦合应用，发展为独立 vLLM GPU 推理服务和 native 回退路径。

综合判断：系统已经达到“可用于实际项目辅助审查和阶段性交付”的技术成熟度，但尚未达到“无需人工复核、测试证据完整、版本不可变且灾备闭环”的状态。因此适合进入结题验收阶段，正式签字前仍需完成本计划列出的发布、测试、真实样本和恢复工作。

## 5. 验收方案

### 5.1 功能验收用例

至少选择一个包含 1 份招标文件和 3 家投标人的真实脱敏项目，完整执行以下用例：

| 编号 | 验收内容 | 通过标准 |
| --- | --- | --- |
| F01 | 登录和退出 | 正确账号可登录；错误密码受控；退出后无法访问业务页 |
| F02 | 用户管理 | 管理员可新增、停用、改级和重置密码；非管理员不可进入用户管理 |
| F03 | 文件夹上传 | 正确结构成功创建项目并绑定投标人；错误结构给出明确提示 |
| F04 | 同名项目隔离 | 再次上传同名项目返回冲突提示，不向已有项目追加文件 |
| F05 | 手工上传 | 招标文件与每组商务标、技术标一一绑定且投标人不串项目 |
| F06 | 分阶段 OCR | 状态按招标、商务、技术阶段推进；页面显示文件及页码进度 |
| F07 | OCR 恢复 | 中断后只处理未完成文件，不重复覆盖已完成文档 |
| F08 | 招标文件审查 | 可上传、筛选通过/异常/待复核、定位原页、重审和删除历史 |
| F09 | 商务标审查 | 五类形式审查能生成结果并正确关联投标文件 |
| F10 | 专项审查 | 偏离、商务查重、技术查重和人员复用按状态门控执行 |
| F11 | 人工复核 | 能定位 PDF、修改可编辑内容、保存草稿、重审并保留结果 |
| F12 | 报告导出 | Word/JSON 可下载；Word 标题、投标人、文件属性、结论、文件名和页码正确 |
| F13 | 数据隔离 | 多个项目轮流查看和导出时，投标人、文件和结果不串项目 |

### 5.2 性能和稳定性验收

1. 采用代表性扫描质量和页数的真实项目，记录上传、OCR、单项分析和导出耗时。
2. OCR 长任务运行期间，前端进度可持续更新，后端无 OOM 和异常重启。
3. 连续完成不少于 3 个项目的全流程，结果归属正确。
4. 应用容器重启后项目、结果和报告仍可查询。
5. vLLM 不可用时应给出可识别错误；按部署指南切回 native 后端能够恢复。
6. 前端、后端和 vLLM 的健康检查连续运行至少一个工作日无异常重启。

性能基线应以本次验收实测数据为准，不直接把历史实验值作为合同验收值。

### 5.3 自动化测试现状

2026 年 9 月 7 日在当前生产容器执行 `unittest` 自动发现：成功执行 47 个用例，另有 1 个实验测试模块因缺少 `experiments.db4ai_edge_1_5b` 导入失败；生产镜像未安装 `pytest`，因此 `test_project_ocr_resume.py` 中 4 个 pytest 风格用例未被本次 `unittest` 执行。

该结果不能表述为“全量测试通过”。正式验收前应：

1. 把测试依赖放入独立开发/CI 依赖，不要求生产镜像安装 pytest。
2. 修复、迁移或从生产测试集排除缺失实验模块。
3. 在 CI 中统一执行 pytest，并保存完整报告。
4. 为前端补充至少一条登录至报告导出的端到端冒烟测试。
