# XTJS 智能审标平台 · 云化部署指南

> 本文档记录当前生产环境的完整部署方式：本机运行应用与前端，数据库/文件/缓存全部使用阿里云托管服务。

## 1. 架构总览

| 组件 | 承载 | 位置 |
|---|---|---|
| 应用 `project-xtjs` | FastAPI + OCR + 分析 | 本机 Docker :8080 |
| vLLM 加速 `xtjs-vllm` | PaddleOCR-VL-1.5 推理服务（OpenAI 兼容） | Docker 内网 `xtjs-vllm:8000`（不暴露公网） |
| 前端 `xtjs-frontend` | React + nginx | 本机 Docker :80（/api 反代到应用） |
| 数据库 | PostgreSQL | 阿里云 RDS（xtjs_db） |
| 文件存储 | 对象存储 | 阿里云 OSS（桶 zhaobiaozhushou，实例 RAM 角色零密钥） |
| 缓存 | Redis 兼容 | 阿里云云数据库 Redis/Tair（账号 xtjs_redis） |

本机无需运行 postgres / minio / redis 容器，`docker-compose.yml` 已只保留 app 与 redis 声明（redis 服务已移除，实际缓存走云上）。

## 2. 部署文件说明

| 文件 | 作用 |
|---|---|
| `Dockerfile.lean` | 精简 GPU 镜像：python:3.12-slim + 清华 PyPI + paddle BOS 源；apt/pip 均走国内镜像 |
| `docker-compose.lean.yml` | 覆盖 app 构建使用 `Dockerfile.lean` |
| `Dockerfile.vllm` | vLLM 0.22.1 推理服务镜像（FlashAttention + CUDA 图，官方支持 PaddleOCR-VL 系） |
| `docker-compose.vllm.yml` | vLLM 服务声明：挂载模型卷、`--served-model-name=PaddleOCR-VL-1.5-0.9B` |
| `XTJS-frontend/Dockerfile.frontend` | 前端镜像（node 构建 + nginx 托管） |
| `XTJS-frontend/nginx.conf` | /api、/health 反代到 `app:8080` |
| `.env` | 全部敏感配置（数据库/缓存/认证/存储），不入库 |

启动命令（在 `project-XTJS` 目录）：

```bash
docker compose -f docker-compose.yml -f docker-compose.gpu.yml -f docker-compose.lean.yml -f docker-compose.vllm.yml up -d --build
```

vLLM 服务首次启动需下载 vLLM/torch 依赖（约 8GB，清华源）并加载模型（约 1–3 分钟），之后常驻；应用启动时不再本地加载 0.9B VL 权重。

前端容器为独立运行（复用同一网络）：

```bash
docker build -t xtjs-frontend -f ../XTJS-frontend/Dockerfile.frontend ../XTJS-frontend
docker run -d --name xtjs-frontend -p 80:80 \
  --network project-xtjs_app_network xtjs-frontend
```

## 3. 云资源准备

### 3.1 阿里云 OSS（文件存储）
- 桶：`zhaobiaozhushou`（cn-hangzhou，私有）
- 凭证：**ECS 实例 RAM 角色**（无需 AK）。创建 RAM 角色 → 授权该桶对象读写 → 绑定到 ECS 实例
- 角色策略需包含：`oss:PutObject/GetObject/DeleteObject/ListObjects/GetBucketInfo/GetBucketLocation/GetBucketLifecycle`
- 生命周期：`cache/previews/` 7 天删除；`JSON识别/` 30 天转低频（勿转归档，程序需实时读）

### 3.2 阿里云 RDS PostgreSQL（数据库）
- 与 ECS 同 VPC，使用内网地址；白名单加入 ECS 私网 IP
- 数据库 `xtjs_db`，高权限账号（需能 `CREATE EXTENSION pgcrypto`）

### 3.3 云数据库 Redis / Tair（缓存）
- 与 ECS 同 VPC，白名单加入 ECS 私网 IP
- 账号密码以 `redis://账号:密码@内网地址:6379/0` 连接（统一 db0）

## 4. `.env` 关键配置

```bash
# 数据库（RDS 内网地址）
DATABASE_URL=postgresql://<账号>:<密码>@<rds内网地址>:5432/xtjs_db

# 对象存储（OSS 内网端点；AK 留占位符时自动走实例 RAM 角色）
MINIO_ENDPOINT=oss-cn-hangzhou-internal.aliyuncs.com
MINIO_ACCESS_KEY=请填写RAM子账号AccessKeyID   # 留占位 = 实例角色模式
MINIO_SECRET_KEY=请填写RAM子账号AccessKeySecret
MINIO_SECURE=true
MINIO_REGION=cn-hangzhou
MINIO_BUCKET_NAME=zhaobiaozhushou
MINIO_ALLOWED_EXTENSIONS=pdf,png,jpg,jpeg,bmp,tif,tiff

# 缓存（云 Redis/Tair）
XTJS_CACHE_REDIS_URL=redis://xtjs_redis:<密码>@<redis内网地址>:6379/0
CELERY_BROKER_URL=redis://xtjs_redis:<密码>@<redis内网地址>:6379/0
CELERY_RESULT_BACKEND=redis://xtjs_redis:<密码>@<redis内网地址>:6379/0

# 认证（务必改）
JWT_SECRET_KEY=<openssl rand -hex 32 生成>
AUTH_INITIAL_ADMIN_USERNAME=admin
AUTH_INITIAL_ADMIN_PASSWORD=<初始管理员密码，首次启动创建>
```

## 5. 首次初始化

1. 启动后访问 `http://<主机>:8080/docs` 查看接口；前端 `http://<主机>/`
2. 使用初始管理员登录后立即改密
3. **首次 OCR 会自动下载 PaddleOCR-VL 模型**（约 2GB，百度 BOS 源，缓存于 `/app/.ocr_runtime`，无需人工干预）
4. 数据库迁移：已有数据用 `pg_dump | psql` 迁移；全新环境由 Flyway 手动执行（见下）

## 6. 日常运维

```bash
# 日志
docker logs -f project-xtjs
# 重建应用（仅代码层，pip 层有缓存，很快）
docker compose -f docker-compose.yml -f docker-compose.gpu.yml -f docker-compose.lean.yml up -d --build

# 备份（RDS 控制台自动备份；文件在 OSS 自带冗余；如需导出）

```

数据库结构变更（Flyway 服务已从 compose 移除）：

```bash
docker run --rm -v "$PWD/db/migration:/flyway/sql" flyway/flyway \
  -url=jdbc:postgresql://<rds内网地址>:5432/xtjs_db \
  -user=<账号> -password=<密码> migrate
```

## 7. 常见问题

- **前端 502**：`docker restart xtjs-frontend`（nginx 启动时解析 `app` 容器 IP，应用重建后 IP 变化）
- **OCR 报 `model does not exist` 或连接超时**：vLLM 服务未就绪。检查 `docker ps` 中 `xtjs-vllm` 状态，用 `docker exec project-xtjs curl -s http://xtjs-vllm:8000/v1/models` 确认返回 `PaddleOCR-VL-1.5-0.9B`；就绪后再重建/重启 `project-xtjs`。
- **vLLM 显存不足**：默认 `--gpu-memory-utilization=0.35`（约 16GB），与其它 GPU 任务冲突时可调低并重启服务。
- **登录被拒/无法建项目**：检查 RDS 白名单与 `.env` 的 `DATABASE_URL`
- **健康检查 cache 非 healthy**：检查云 Redis 白名单与 `XTJS_CACHE_REDIS_URL`
- **上传 500/403**：检查 OSS 实例角色是否仍绑定、角色策略是否含对象读写
- **磁盘空间**：镜像约 20GB + OCR 模型 2GB；`docker builder prune` 可清理构建缓存

## 8. OCR 性能（vLLM 加速）

- 原生 paddle 推理后端（`PADDLE_VL_BACKEND=native`）：约 **3.3 秒/页**（L20 实测）。
- vLLM 服务端推理（`PADDLE_VL_BACKEND=vllm-server`）：合成文档稳态 **0.22–0.28 秒/页**；真实扫描件 **0.57–0.67 秒/页**（2025-369 项目 2887 页实测，含 `use_queues=true`）；识别文本与原生后端一致性 0.997。
- 首个请求含 vLLM CUDA 图预热（约 1–7s），之后进入稳态。
- 关键开关（`.env`）：
  - `PADDLE_VL_BACKEND=vllm-server`、`PADDLE_VL_SERVER_URL=http://xtjs-vllm:8000/v1`（应用接入 vLLM）
  - `PADDLE_VL_USE_QUEUES=true`（vLLM 后端下开启页级 CPU/GPU 流水线重叠，实测 **+34%**；原生后端下无收益）
  - `PADDLE_OCR_USE_DOC_ORIENTATION/UNWARPING=true`（关闭无收益，保留以兼容倾斜/扫描件）
- 回退原生：`.env` 中 `PADDLE_VL_BACKEND` 改回 `native` 并重建应用容器即可，无需改动其它配置。
- **多文档并发实测结论**：单卡 L20 上双 OCR 实例并发会使总吞吐下降（vLLM 跨文档请求交错降低批处理效率，布局模型与解码抢 GPU），仅墙钟快 ~15% 且单文档变慢 70%，故保持串行文档队列（`PADDLE_OCR_MAX_INFLIGHT_PER_DEVICE=1`）。进一步提速方向：FP8 量化或更高带宽 GPU。
