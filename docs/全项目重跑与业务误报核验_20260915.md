## 查重、人员及展示的补充发现

- **重复内容真实存在，风险含义需要收窄。** 两个位育项目的技术查重证据含许可证固定说明、“投诉举报电话12315”、统一承诺和目录。商务查重也含“我公司完全响应，无偏离”和相同合计金额。这些文字重复不能单独证明抄标或串标。应显示重复来源和证据性质，不能因为公共模板相同直接提高风险结论；同一文件双角色扩大技术查重范围属于此前明确暂缓的已知限制，本轮未改。
- **人名候选误提取。** 两个位育项目天焮第87页考核表的“工作态度”被当作人名，角色却是“是否严格遵守工作纪律……”。这是表格类型/姓名列识别错误，不是姓名 OCR 字形错误。人员模块仍要求人工确认，本轮没有确认该伪人名，也没有把候选数量等同于真实在岗人员数。
- **待确认与没有问题的展示需要区分。** 位育人员提取结果为 `confirmation_status=pending`，总览人员模块却显示“0项／未发现该类问题”。这不等于已经确认无人员复用；建议明确显示“待确认人员名单”，与已确认后无复用区分。2026-249 等既有人工确认结果仍应优先使用，不能用新一轮未确认草稿覆盖。
- **单位名称展示混入文件名。** 部分条目显示“公司全称＋投标（响应）文件＋商务”等长名称。形式审查无可靠名称时回退了文件名，不能把文件名兜底当已确认主体；应分别展示识别名称、文件名与待确认状态。不能按形近字自动更改公司名称。
- **未核原件的缺件、缺章和对齐疑点仍需复核。** 全量重跑不等于逐页人工鉴定137份PDF；本报告对明确核验的案例给出结论，对其余条目保留原告警及证据，不静默删除。

## 建议优先顺序

1. 先处理 S01 签字漏判、S02—S05 分项金额证据错误、S10 附件错配及 S16 包件范围；这些会产生确定失败或错误通过。
2. 再处理 S08—S09 日期定位、S11—S15 组成/模板边界和偏离语句角色。每个修复同时保留真实缺件、真实主动负偏离、正确计算的反例。
3. S06—S07 单价报价与限价证据单独回归；O01—O03 使用原件人工复核或限定页面重识别，不做字符替换。查重公共文本和人员候选另列小范围计划。
4. 本次仅执行重跑、核验与报告，**没有修改业务代码、原始文件或 OCR 文字，也未发起新的人工确认操作**。逐次调用检查未发现既有人工确认内容改变；收到停止指令后未再执行最终数据库全量对账。上述是建议，不能当成已经上线的修复。


## 已取得的页面和加载证据

已进行的浏览器访问中，17 个项目最终都能打开结果总览；八一项目首次在 60 秒等待内未取得结果响应，随后重试完整显示约需 **65.45 秒**。该次重试没有记录页面脚本错误、失败响应或写入请求。这个结果说明仍有明显加载性能问题，不能因最终打开成功就判定问题消失。

已保存的一次八一结果快照中，`technical_bid_duplicate_clusters` 展开为 JSON 后约 **306.5 MiB**，完整结果记录约 **347.2 MiB**；这里是解码后数据规模，不是实测网络传输字节数。技术查重聚合重复携带来源问题和定位内容，是需要优先排查的负担。当前证据不能把这次慢加载直接归因于 OSS 故障；停止后没有继续做存储链路或最终结果体积复测。

建议后续限制概览接口载荷、按需读取大明细并减少重复嵌入来源内容，保留历史对象。此次没有实施这些改动。
